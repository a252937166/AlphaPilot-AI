## 架构师签认前必须人工核对的边界

1. **合同原件缺失是 blocker。** 请通过可信渠道补回原始 contract JSON；其文件 SHA-256
   必须精确等于 `a16995e...b951`。
2. validator 会验证 PDF/DOCX 内容哈希、来源、固定操作数和结构化摘录，但目前不会直接从
   PDF/DOCX 原文重新 OCR/解析公司行动、财务行项目和交易规则。公告 inventory 与估值 JSON
   已做原始响应重解析。故独立签名人仍须逐份对照这些 PDF/DOCX，不能仅看 summary。
3. builder 会冻结并校验首个成功响应的结构化声明，但不能仅从归档文件独立证明采集器确实
   没有先成功于另一来源；`first_success/fallback/prior_errors` 仍属于需签名人核对的
   provenance 声明，不得描述成密码学证明。
4. 对外 ZIP 排除了 `raw-source` 中 25 个响应 header 文件，其中 9 个包含公共站点短期
   `Set-Cookie` 会话标识；本机冻结源包未改。候选核心 `artifacts/`、原始响应正文、请求记录
   和 SOURCE-MANIFEST 均保留，但外部副本无法对这 25 个已脱敏 header 重新跑全量源包 checksum。
5. 签认阶段不得联网、换源、换样本、改业务键、改本地值或改变容差。
6. 若审阅通过，只允许在候选副本中修改三个顶层字段：

   ```json

     "approved": true,
     "reviewer_role": "独立人工架构师的可识别身份/角色",
     "reviewed_at": "带时区的 ISO-8601 时间"
   }
   ```

   然后将完整签名文件及其整文件 SHA-256 通过可信渠道返回。不得由实现者代签。
7. 收到签名文件后，先把整文件 SHA-256 固定为生产 trust anchor，再以该签名文件复跑
