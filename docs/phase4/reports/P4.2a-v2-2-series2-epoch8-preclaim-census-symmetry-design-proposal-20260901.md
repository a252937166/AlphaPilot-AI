## 2. Root cause and exact blast radius

### 2.1 The asymmetric inventories

The Q-embedded registered preflight ran at execution HEAD `dcd749f4707f6b806249e842e1402d0c12df2fbf`. Its census had:

- 29 references / 29 rows;
- 29 logical sources;
- 3 lawful projections;
- 0 invalid rows;

- ref snapshot SHA-256 `3f15b87276de2b073fe3d2f5b96161222e49cf62a934243bda3466342a1cfc7c`.

At B, recovery start constructed a census with:

- 33 references / 33 rows;
- 33 logical sources;

- 0 invalid rows;

That ref-snapshot digest describes the exact start observation. It is not claimed to be reproducible after later design refs exist; the immutable 29→33 row comparison and both registry digests are the root-cause evidence.

The 29 shared rows were byte-identical. No baseline row was missing or mutated. The four additions were:

1. the epoch-7 landing record;
2. Q;
3. R;
4. B.

The start-delta validator correctly removes only Q/R/B from the set of newly admitted rows. The landing record remains as an unexpected fourth row and the start fails closed.

### 2.2 The implementation defect

The registered preflight currently constructs its additional census references from only:

- owner exact surface authority; and
- independent implementation review.

The recovery-start helper constructs its additional references from:

- owner exact surface authority;
- independent implementation review;
- landing report; and then
- Q/R/B.

The approved epoch-7 design required the preflight inventory to include the current epoch's authority, review, **and landing**, with start adding only Q/R/B. The implementation omitted landing only on the real registered-preflight path. An exact-OS helper manually fabricated a baseline census that already contained landing, so the test passed without exercising the defective real preflight path.

### 2.3 What is not defective

The following controls remain correct and must not be weakened:

- the strict `baseline + Q/R/B` row equality;
- the requirement that all baseline rows remain byte-identical;
- the exact first-parent Q→R→B topology;
- the rule that only `main` and `origin/main` may move from preflight to B;
- all-ref census traversal and lawful-projection classification;
- ref snapshots before and after each census;
- zero-write preflight policy;
- authorization consumption only at atomic claim creation;
- ledger/mirror read-only invariants;
- dual historical/live byte anchors;
- zero pipeline start and zero automatic retry.

The repair must not add a special-case whitelist for the epoch-7 landing path, subtract a fourth row at start, omit landing from start, or accept “at least baseline plus Q/R/B”. Those approaches would conceal future baseline omissions and weaken the control.

## 4. Normative repair

### 4.1 Explicit landing input to registered preflight

The `--preflight-only` mode gains an explicit `--landing-report <absolute path>` argument for the current live recovery epoch. The caller must supply the exact landed report path. The implementation must not derive it from a date, glob, branch name, remembered filename, latest-file scan, default, environment variable, or repository search.

For historical registered preflight fixtures that intentionally predate the recovery capability, the parser may preserve their existing mode-specific behavior. For epoch 8 and any future live recovery epoch, absence of `--landing-report` is a parse-time or immediate fail-closed validation error before any storage read.

`--landing-report` is valid only with `--preflight-only`. Supplying it with active `--execute`, `--recover-sealed-bundle`, `--consume-recovered-release`, or any unregistered mode fails at argument validation before identity, storage, ledger, bundle, or temporary-path access.

The preflight validates the supplied landing report as a first-class `AuthorityReference`:

- it is under the registered reports directory and is the exact normalized path supplied by the caller;
- it is a non-symlink regular file with canonical registered bytes;
- its digest and creating commit are derived from real bytes and real Git history, never from a constant fallback;
- it is a unique-`A`, single-parent child of the declared two-parent merge;
- the merge's first and second parents, implementation, review projection, owner authority, control root, counts, and report bytes agree with the current live epoch contract;
- its creating commit is an ancestor of the preflight execution HEAD;
- HEAD/worktree bytes equal the pinned landing bytes.

Any missing file, bad topology, wrong digest, unexpected path, alias, duplicate source, or ref drift fails closed.

### 4.2 One shared baseline specification

Producer code builds one typed current-epoch authority tuple:

```text
owner surface authority
independent implementation review
landing report
```

The registered preflight passes that exact tuple to both of its real-lineage census snapshots. It must not rebuild the tuple differently for the recheck.

Recovery start derives the same three typed references from the R `execution_epoch`, then appends exactly Q, R, and B. The existing strict delta predicate remains:

```text
start rows - {Q, R, B} == baseline rows
AND every baseline row is byte-identical
AND Q, R, B are all present
```

The Git-ref delta remains exactly the linear Q→R→B advancement of `main` and `origin/main`. No unrelated commit, branch movement, new ref, deleted ref, or changed baseline row is absorbed.

### 4.3 Preflight output and Q binding

The registered preflight remains one canonical JSON stdout line with empty stderr, natural `rc=0`, all effects zero, and before/after fingerprints equal. Its full census now necessarily includes landing. Consequently its census bytes, SHA-256, row/reference counts, registry SHA-256, stdout bytes/SHA-256, and control root are fresh epoch-8 values; none may be copied from epoch 7.

The new Q embeds those exact stdout bytes. Q, proposed R, R, and B independently bind the same census reference. Recovery start parses and canonicalizes the embedded stdout, compares it to the R reference, and verifies the strict delta before storage probing or claim creation.

### 4.4 Independent validator

The validator must independently reconstruct the producer's census specification from the epoch-8 contract and actual Q/R/B bytes. It must not trust producer-reported row counts, reference counts, registry digests, classifications, or work counters.

During passive bundle validation it must prove:

- Q's embedded preflight census includes owner, review, and landing;
- the start census is exactly that baseline plus Q/R/B;
- every baseline row and raw touch is unchanged;
- Q/R/B topology and ref delta are exact;
- the live epoch-8 anchor and historical selected epoch-6 anchor remain separate;
- no active replay, attempt allocation, pipeline, model, held-out, database, or trading path is reachable.

This closes the already-approved epoch-7 design requirement that the validator independently recompute the census rather than merely accept a producer summary.

## 5. Recovery document compatibility

### 5.1 Q schema correction

The epoch-7 Q wire key `landed_epoch_7` is not semantically valid for a newly landed epoch 8. Reusing it with nested `epoch: 8` would turn a historical name into an undocumented alias and create another imagined-field trap.

Epoch 8 therefore introduces only this review-request schema revision:

```text
schema_version:
  p4.2a-v2-2-series2-sealed-bundle-recovery-review-request-v2

exact top-level field replacement:
  landed_epoch_7 -> landed_execution_epoch
```

The Q remains exactly 13 top-level fields; the replacement object retains the same exact eight nested fields. The semantic value is the latest fully landed live execution epoch and therefore binds epoch 8.

The 19-field R, 12-field B, claim, recovery terminal, and mirror-receipt schemas are already epoch-neutral and remain byte-for-byte contract-compatible at version `v1`. Their new document instances necessarily receive fresh bytes and digests because they bind epoch 8 and the new preflight. No producer or validator fallback accepts Q v1 in an epoch-8 recovery chain.

The epoch-8 companion must declare this mixed exact schema set explicitly. Unknown fields, aliases, defaults, best-effort parsing, and dual acceptance are forbidden.

### 5.2 Registered preflight schema correction

The epoch-7 preflight stdout schema also exposes an epoch-specific live key, `epoch_7_recovery_storage`. Embedding that key in Q v2 would falsely label the epoch-8 live storage proof and would contradict the no-alias rule in section 5.1.

Epoch 8 therefore introduces:

```text
schema_version:
  p4.2a-v2-2-read-only-implementation-preflight-v2

exact top-level field replacement:
  epoch_7_recovery_storage -> registered_recovery_storage
```

All nested storage fields and their strict semantics remain unchanged: both owner-provisioned containers, canonical unaliased paths, device/inode, owner uid, mode `0700`, non-symlink status, emptiness, and zero created leaves. The new name identifies the registered live recovery storage without pretending it belongs permanently to epoch 7.

Every preflight with `implementation_epoch=8` emits v2 and the new key, in both `REGISTERED_OFFICIAL` and `NONREGISTERED_READ_ONLY_TEST` modes. The official root requires the strict `registered_recovery_storage` object; a synthetic nonregistered root may retain the existing mode-specific `null` value while preserving the identical v2 top-level schema. Only explicitly historical fixtures with implementation epoch below 8 may emit or consume preflight v1.

Q v2 embeds and parses those exact v2 stdout bytes and binds their SHA-256, byte count, status, stderr count, and return code. R v1 remains 19 fields and binds only the `real_lineage_census` reference extracted from that stdout; it does not gain stdout fields. B v1 binds Q's preflight stdout SHA-256, byte count, status, and census SHA-256. Recovery start and validator independently cross-check that Q's full preflight, R's census reference, and B's preflight reference all describe the same v2 result. The epoch-8 recovery path rejects preflight v1, the old `epoch_7_recovery_storage` key, both keys together, missing keys, aliases, and unknown fields.

Frozen epoch-7 preflight v1 bytes remain historical evidence and historical tests may continue to parse or hash them in their explicitly historical context. They are never accepted as the current epoch-8 preflight.

### 5.3 Old chain disposition

The existing Q/R/B remain valid evidence of one owner-authorized, non-consuming preclaim refusal. They are not rewritten, deleted, amended, or reused. Their old authorization hash must never name an epoch-8 claim, stage, snapshot, or receipt.

After epoch-8 landing:

1. rerun the real registered-root preflight with the explicit epoch-8 landing report;
2. create a fresh Q v2 as a unique `A` on then-current `main`;
3. obtain an independently reviewed, byte-identical fresh R;
4. obtain a new transcript-bound owner confirmation and land a fresh B;
5. run exactly one recovery start under that new R/B.
