## 2. Root cause

The epoch-8 surface authority has two legitimate Git appearances with one
logical byte identity:

| Role | Commit | Parents | Authority SHA-256 |
|---|---|---|---|
| logical source | `73a703a422b5209115f5b244490db36e06b1f15d` | `[a39c0263fefcfbdb1886100fec1b71ec374b43a4]` | `4547a2231c23a0fff96dced033028c279c4247c76130e79360e2ec602f8dd016` |
| lawful first-parent merge projection | `d9838923b54932eee1785c209b1ff85fbdf8d523` | `[7b9aa18372410baa5d96bd9560fa10a2c6a3d8ac, ef701e326ebf77e5f18d48544f1da5975253cd5b]` | same bytes and SHA-256 |

At the registered landing HEAD, `_authority_reference_for_path` calls
`_unique_a_commit_for_path`. That helper scans only the execution HEAD's
first-parent history, so it observes the merge projection `d9838923...` as the
single `A` and reports that projection as `AuthorityReference.creating_commit`.

`validate_implementation_epoch` then calls `_later_epoch_surface`, which
correctly interprets `creating_commit` as the logical source and requires it to
be the direct child of the authority document's `base_commit`. The document's
base is the epoch-8 companion `a39c0263...`; the true source `73a703a4...` is
its direct child, while the merge projection is not. The two helpers therefore
assign incompatible meanings to the same field and fail at the intended strict
predicate.

The existing runner test
`test_epoch_seven_unique_a_accepts_only_a_byte_identical_first_parent_projection`
made the gap explicit but did not close it: it expected
`validate_unique_a_authority` to reject a source reference after a lawful
projection, while separately proving that `_classify_unique_a_lineage` accepts
the same source plus projection. The epoch-8 exact-OS fixture never drove the
registered preflight's path-to-reference discovery through this real topology.

The validator already contains an independent, stricter model:
`_discover_authority_source` plus `_classify_authority_touches`. It identifies
one logical single-parent source and permits only byte-identical lawful
first-parent projections. The producer preflight failed before the validator
could consume a source-bound reference.

## 3. Security purpose and invariant

The repair must not redefine unique-A as “any identical copy is acceptable.”
It must preserve this exact invariant:

1. There is exactly one logical source commit.
2. The source is a single-parent exact `A`; its parent lacks the path.
3. The source payload matches the pinned SHA-256 and current worktree bytes.
4. Every other path touch is a two-parent first-parent merge projection.
5. For each projection, the source is reachable from the merge's second parent.
6. The merge commit's blob equals the source blob byte-for-byte.
7. The second-parent-to-merge diff for the path is empty.
8. No modification, deletion, rename, copy alias, extra source, third touch, or
   ambiguous source is accepted.
9. The source—not its projection—continues to satisfy the companion-parent and
   implementation-child topology checks.
10. Current-byte, require-current, loaded-module, census, and ref-freeze checks
    remain unchanged.

This retains the anti-tamper purpose: a merge projection is merely a lawful
first-parent representation of an already pinned source blob. It cannot create
authority, change authority bytes, change the source's parent, or hide another
touch.

## 4. Producer algorithm

### 4.1 Make the requested identity role explicit

`_authority_reference_for_path` must take a closed, required identity-mode
enum with no default. The two permitted modes are:

- `LOGICAL_SOURCE_WITH_LAWFUL_PROJECTIONS`;
- `FIRST_PARENT_VISIBLE_UNIQUE_A`.

All initial and final snapshot calls for the same argument must reuse the same
mode. Aliases, strings outside the enum, or an omitted mode fail before Git or
storage access.

The existing first-parent-only `_unique_a_commit_for_path` remains unchanged
for Q/R/B and other action documents whose contract really is one unique-A on
the registered first-parent chain. Broadening that helper globally would blur
two distinct contract meanings and is outside this repair.

For `LOGICAL_SOURCE_WITH_LAWFUL_PROJECTIONS`, add bounded logical-source
discovery:

1. Normalize the repository-relative path and read the current regular,
   unaliased worktree bytes once.
2. Enumerate that path's all-ref touches with the existing
   `--diff-merges=first-parent` representation; do not retain unrelated blob
   payloads.
3. Form source candidates only from exact-path `A` touches whose commit has one
   parent and whose parent lacks the path.
4. For each candidate whose blob equals the current bytes, invoke the existing
   producer-independent `_classify_unique_a_lineage` semantics with the
   candidate as `PINNED_SOURCE`.
5. Accept only one candidate whose classification is
   `PASS_ONE_LOGICAL_SOURCE_AND_ONLY_LAWFUL_PROJECTIONS`, with one source, zero
   invalid touches, and the source on the execution-head lineage.
6. Return an `AuthorityReference` whose `creating_commit` is that logical
   source and whose SHA-256 is over the source/current bytes.

Zero candidates, two candidates, a worktree mismatch, or any invalid touch is
fail-closed. Discovery must process candidates one at a time and must not cache
whole-history payloads. Existing Git-work upper bounds remain effective; no
timeout, threshold, retry, or concurrency setting changes.

For `FIRST_PARENT_VISIBLE_UNIQUE_A`, retain the existing strict
`_unique_a_commit_for_path` behavior and return the visible first-parent A.

### 4.2 Validate the owner as a source identity

Add a dedicated source-with-projections validator, or invoke the existing
`_classify_unique_a_lineage` directly from `_later_epoch_surface`, for the
owner surface authority. Do not change the global semantics of
`validate_unique_a_authority`. The source-aware validation must:

- require the supplied path/SHA/source tuple;
- require the source and execution HEAD to resolve to commits;
- require the source to be on the execution lineage through a lawful
  projection;
- rehash the source blob and current worktree file;
- require exactly one logical source and only lawful projections.

After that classification passes, `_later_epoch_surface` keeps its existing
source-to-base and implementation-to-source direct-parent checks unchanged.

### 4.3 Owner, review, and landing use different registered roles

The epoch-8 registered preflight call sites are explicitly bound as follows:

- owner surface authorization uses
  `LOGICAL_SOURCE_WITH_LAWFUL_PROJECTIONS` and returns source
  `73a703a4...`, not merge projection `d9838923...`;
- independent implementation review uses `FIRST_PARENT_VISIBLE_UNIQUE_A` and
  returns merge projection `d9838923...`, because the registered landing
  contract intentionally treats that field as the two-parent projection and
  separately proves that its second parent is review source `ef701e32...`;
- landing report uses `FIRST_PARENT_VISIBLE_UNIQUE_A` and returns its direct
  first-parent source `87c73ce...`.

The existing specialized epoch-8 landing topology validation remains
unchanged: it derives the review source from the merge's second parent, proves
that parent is the candidate's reviewed child, proves the projection bytes are
identical, and proves the landing-record shape. Converting the review reference
to source `ef701e32...` would be another role collision and is forbidden.

The minimal justified surface is two modified paths:

must not infer this draft surface if review changes it.

## 6. Registered tests

### 6.1 Real Git positive

Build a temporary repository with the same shape as the registered landing:

1. base on the future first parent;
2. companion then source authority on a side branch;
3. implementation and independent review as direct single-parent descendants;
4. advance the first parent independently;
5. no-ff merge the review branch;
6. add a unique-A landing report as the merge's direct child;
7. invoke the real role-aware path-to-reference resolver at that landing HEAD.

Assert that the owner reference names its side-branch logical source, the
review reference names the two-parent merge projection, and the landing names
its first-parent source. The authority remains a direct child of its companion,
the implementation remains a direct child of the authority, the review source
is the merge's second parent and candidate child, and the preflight returns the
registered v2 schema with zero effects.

### 6.2 Exact-OS positive

Run the locked shim in a synthetic repository with the same source/projection
topology and explicit landing argument. It must reach
`PASS_READ_ONLY_IMPLEMENTATION_PREFLIGHT`; a fabricated preflight document is
not a substitute.

### 6.3 Negative matrix

Each case must fail before storage probing and leave all fingerprints equal:

- projection blob differs from source;
- second-parent-to-merge diff is non-empty;
- source is not reachable from the projection's second parent;
- source has two parents or its parent already has the path;
- source is not the companion's direct child;
- implementation is not the source authority's direct child;
- second logical source with equal bytes;
- later `M`, `D`, rename, copy, or third non-projection touch;
- current worktree bytes differ;
- supplied SHA, source commit, or requested identity mode differs;
- owner is requested as a projection or review is requested as a source;
- landing report is missing, aliased, outside reports, or has wrong topology.

The existing generic first-parent projection test remains truthful: generic
first-parent authority validation rejects a side-branch source reference. New
tests prove that the explicitly source-aware resolver accepts exactly one
logical source plus lawful projection for the owner and that no other call site
can accidentally select that mode.

### 6.4 Coverage and performance

- Runner collect count may not fall below the epoch-8 registered `230`.
- Validator collect count may not fall below `323`, even if its bytes are
  unchanged.
- F-15 runs both complete registered modules.
- Independent F-12 reruns both complete modules; no epoch-8 result is inherited.
- A targeted exact-OS preflight positive runs before the long modules.
- A deterministic counter asserts bounded path touches, Git object reads, and
  subprocess calls for each source resolution so a future history-dependent
  blow-up fails fast.

## 7. Epoch and historical-state rules

- The repair is implementation epoch `9`; epoch-8 landed bytes remain immutable
  historical governance evidence.
- The sealed series still has attempts `[1,2]` with implementation epochs
  `[5,6]`; no synthetic epoch row is added to the sealed bundle.
- Series token, history root, live ledger root, selected ordinal, ledger bytes,
  sealed snapshots, and mirror receipts remain unchanged.
- The failed epoch-8 preflight creates no reusable preflight authority and no
  Q/R/B.
- Epoch-9 must create a fresh landing report, then one fresh registered-root
  preflight and fresh Q v2/R v1/B v1 before any recovery start.
- After that preflight, main and registered refs freeze except for exact Q/R/B.
- Recovery remains exactly one start, zero pipeline starts, and zero automatic
  retry only after fresh R and transcript-bound B authorize it.
