## 6. One-start claim and recovery state machine

### 6.1 Linearization point

The final R canonical SHA-256 determines the claim name:

`CLAIM-<R_SHA256>`

One atomic `mkdir(mode=0700)` of that exact path in the primary recovery container is the sole recovery-start linearization point.

- Failure before successful `mkdir`: no recovery start is consumed, but the operator still performs no automatic retry.
- Successful `mkdir`: the one authorized recovery start is permanently consumed, even if no later file is durable.
- Any pre-existing claim path, including empty or partial, rejects the call.
- A second invocation with the same R always rejects.

## 7. Recovery algorithm and bundle-mirror protocol

After bootstrap, R/B, the live anchor, census and all preclaim checks pass, the single recovery does exactly this:

1. Validate the sealed ledger through a pure read-only parser as closed, with exactly one selected validated candidate at ordinal 2 and exact section-1 roots/counts/files. `SeriesLedger.open` is unreachable in recovery, including read mode.
2. Validate both through-ordinal sealed snapshots and all paired receipts; require the final through-ordinal-2 snapshot and receipt bindings in section 1.
3. Fingerprint the sealed ledger and sealed mirror inputs.
4. Require the official destination, exact claim, destination stage, secondary-snapshot stage, secondary snapshot and both future receipt paths absent.
5. Atomically create the claim; write and re-read canonical `started.json`.
6. Rehydrate the already sealed run-A/run-B archives and attempt history from ledger/snapshot bytes. Do not call any pipeline or replay function.
7. Construct the unchanged series-2 bundle in the destination stage with exactly two epoch rows: epoch 5/ordinal 1 and epoch 6/ordinal 2 selected.
8. Run independent passive bundle validation against the destination-stage bytes. No active replay is available in recovery mode.
9. Recheck the epoch-7 live anchor and real-lineage census immediately before publication.
10. Atomically publish the official destination directory with no replacement.
11. Copy the published destination into the distinct secondary-snapshot stage whose final name is derived from R SHA and published tree root.
12. Atomically publish that snapshot with no replacement.
13. Compare the complete destination and snapshot inventories, bytes, per-file hashes and tree roots.
14. Re-fingerprint all sealed inputs and require byte-for-byte equality with step 3.
15. Only after step 14 proves the facts, construct one canonical bundle-mirror receipt declaring those facts and create it byte-identically in the primary and secondary recovery containers.
16. Re-read both receipts and prove equal bytes, SHA and byte count.
17. Re-fingerprint all sealed inputs again and require equality with both step 3 and step 14; revalidate the receipt claims against this final observation.
18. Prove the destination stage and secondary-snapshot stage absent as a consequence of their successful atomic renames.
19. Write success terminal only after every preceding condition passes.
20. Emit one canonical JSON stdout line; stderr is empty on success.

The recovery must never call `SeriesLedger.open` in any mode, attempt allocation, candidate/terminal writers, `replay_selected_pipeline`, `_execute_pipeline_inner`, active bundle replay, active release replay, model/network/database/held-out readers, or any trading code. It reads the sealed ledger only through side-effect-free file descriptors and the pure history validator. Fail-if-called canaries register this negative capability.

The bundle-mirror receipt schema version is `p4.2a-v2-2-series2-bundle-recovery-mirror-receipt-v1` and has exactly:

`schema_version`, `recovery_authorization_sha256`, `owner_confirmation_binding_sha256`, `recovery_id`, `series_id`, `series_token_sha256`, `sealed_history_root_sha256`, `sealed_live_ledger_root_sha256`, `selected_attempt_ordinal`, `selected_implementation_epoch`, `selected_implementation_commit`, `execution_epoch`, `execution_implementation_commit`, `execution_head`, `destination`, `published_bundle_sha256`, `published_tree_sha256`, `secondary_snapshot`, `secondary_snapshot_tree_sha256`, `destination_and_snapshot_byte_identical`, `pipeline_starts`, `automatic_retry_count`, `sealed_ledger_before_after_equal`, `sealed_mirror_before_after_equal`, `verified_at_utc`.

The receipt contains neither its own path nor its own digest, so the primary and secondary copies can be byte-identical. Its filename is:

`recovery-<R_SHA256>-<PUBLISHED_TREE_SHA256>.bundle-mirror-verification.json`

Crash states are fail-closed:

- empty claim: consumed, owner reconciliation required;
- started but no destination: consumed failure, no retry;
- destination without secondary snapshot: consumed, owner reconciliation required;
- snapshot without two receipts: consumed, owner reconciliation required;
- one receipt only: consumed, owner reconciliation required;
- two receipts without success terminal: consumed, owner reconciliation required;
- success terminal is acceptable only with destination, snapshot and paired receipts all independently revalidated.

The bundle then goes to the independent review described in the adjudication. Epoch 7 does not add a release-consumption CLI and does not create a release authorization.

### 8.3 Why the anti-tamper coverage is preserved

The old conjunction was accidentally stronger in the wrong dimension:

```text
archived selected bytes == selected Git blobs == current worktree bytes
```

That expression makes any later reviewed fix impossible to execute. Epoch 7 replaces it with the intended two-moment conjunction:

```text
sealed selected bytes == immutable epoch-6 Git blobs
AND
executing bytes == latest landed and reviewed epoch-7 Git blobs
```

No evidence is trusted with fewer checks:

- selected started/candidate/terminal bytes, history root, evidence root, control archive, harness identity and run-A/run-B roots still bind to the exact attempt implementation commit;
- the bundle still contains only the two executed epochs and the selected candidate still belongs to epoch 6;
- the entire executing control surface and loaded modules bind to the owner-authorized, independently reviewed, first-parent-landed epoch-7 bytes;
- the current anchor is checked before any sealed input read, again before publication, and by the independent validator;
- rehydrated evidence must match the sealed candidate and registered bundle schema exactly;
- pipeline functions are unavailable, so newer code cannot silently regenerate or reinterpret model results.

Thus a mutation of historical evidence fails the historical anchor; a mutation of current code fails the live anchor; swapping the anchors fails typed schema and epoch/topology checks; and a behavior-changing current implementation that constructs different bundle bytes fails passive independent validation. The historical snapshot is not weakened, and current-code tamper detection remains complete.

## 9. Unique-A merge-projection tolerance

### 9.1 Shared classifier

All global-history consumers use one closed `AuthorityCensusSpec` registry and one semantic classifier, independently implemented by producer and validator. Global scanning remains global: no branch-name allowlist, no ignored remote refs, no `HEAD`-only shortcut and no deletion of evidence to make a predicate pass.

Every registered authority must have exactly one logical source, but the contract declares one of four non-inferred roles:

- `PINNED_SOURCE`: the reference's `creating_commit` is the logical source and must be the exact source `A`.
- `PINNED_LANDING_PROJECTION`: the reference's `creating_commit` is the declared two-parent landing projection; the unique logical source is derived from its second-parent lineage, and source, second parent, landing and pinned digest must all carry identical raw bytes.
- `PINNED_SOURCE_WITH_DESCENDANT_GRAPH`: the reference pins the source and retains the stronger initial-sibling descendant byte-invariance/absence proof.
- `DISCOVER_SOURCE_AFTER_PROJECTIONS`: no serialized creating commit is available; remove only proven projections, then require exactly one source `A` and bind it to execution HEAD/worktree.

The role is part of `AuthorityCensusSpec`; runtime data may not choose or downgrade it. In the first and third roles, the pinned creating commit is the logical source. In the second role, the pinned creating commit is intentionally the landing projection and must not be falsely required to equal the derived source.

An additional raw `A` touch is classified as `FIRST_PARENT_MERGE_PROJECTION` only when all of these are true:

1. the touch status for the exact path is `A` relative to first parent;
2. the commit has exactly two parents;
3. the first parent lacks the path;
4. the second parent contains the path with raw bytes exactly equal to the pinned payload;
5. the merge result contains the same raw bytes;
6. the second-parent-to-merge diff for that path is empty;
7. the pinned logical source is an ancestor of the second parent;
8. the pinned payload's recomputed SHA-256 equals the registered digest;
9. no rename, copy, deletion, type change, path substitution or conflict-written different payload is involved.

Raw bytes are compared before digests. A same-digest assertion without raw-byte equality is insufficient.

Every other shape fails: another single-parent `A`, an octopus merge, first parent already containing the file, absent or different second-parent bytes, different merge bytes, a non-empty second-parent-to-merge path diff, a source outside the second-parent ancestry, `M/D/R/C/T`, delete/re-add, malformed Git output, or ref drift during the scan.

### 9.2 The four current all-ref scanners

The current validator contains exactly three `git log --all` scans plus one `rev-list --all --children` scan. Epoch 7 covers all four:

| Current scanner | Required mode |
|---|---|
| `_unique_a_authority` near current line 1922 | `PINNED_SOURCE`: one pinned source plus only lawful projections |
| `_validate_implementation_review_authority.all_touches` near current line 2022 | `PINNED_LANDING_PROJECTION`: exact derived source review and declared pinned landing projection, plus only additional lawful projections |
| `_validate_initial_sibling_authority` near current line 2163 | `PINNED_SOURCE_WITH_DESCENDANT_GRAPH`: retain the stronger descendant byte-invariance/absence proof and classify any visible merge touch with the shared projection rule |
| `_unique_a_unserialized` near current line 2227 | `DISCOVER_SOURCE_AFTER_PROJECTIONS`: remove only proven projections, then require exactly one logical source |
