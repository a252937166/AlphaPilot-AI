## 3. State transition and effect model

The recovery path is a separate operation, not an attempt path:

```text
sealed closed ledger + selected candidate + explicit recovery authorization
                 |
                 v
       read-only history and evidence validation
                 |
                 v
 historical selected-byte anchor + live epoch-5 execution-byte anchor
                 |
                 v
 reconstruct run-a/run-b archives from sealed evidence (no pipeline call)
                 |
                 v
 build unchanged bundle schema with [void1, epoch2, void3, epoch4]
                 |
                 v
 passive independent validation (no active replay)
                 |
                 v
 atomic create-only publication + recovery-claim terminal evidence
```

There is no edge from this flow to attempt allocation, `replay_selected_pipeline`, model inference, network access, production database access, held-out evaluation, or ledger write APIs.

### 5.2 One-start recovery claim outside the sealed ledger

To make “one recovery start, zero automatic retry” machine-enforceable without touching the ledger, the design creates a separate private claim root derived from the recovery-authorization SHA-256, for example:

`<canonical-parent>/.alphapilot-p4-2a-v2-2-bundle-recovery-claim-<authorization-sha256>`

It is not a series ledger and contains no attempt ordinal. Atomic `mkdir(..., 0700)` of this exact root is the sole linearization point for `authorized_bundle_recovery_starts=1`. Before that successful `mkdir`, no recovery start is consumed. After it, the authority is consumed even if the process crashes.

The claim state machine has exact canonical records:

- `started.json`: exactly `schema_version`, `recovery_id`, `authorization`, `created_at_utc`, `created_at_shanghai`, `execution_head`, `execution_epoch`, `sealed_history_root_sha256`, `sealed_live_ledger_root_sha256`, `destination`, `state`, `authorized_bundle_recovery_starts`, `authorized_pipeline_starts`, and `automatic_retry_count`; `state=STARTED` and the counters are `1/0/0`.
- `terminal.json`: exactly `schema_version`, `recovery_id`, `authorization`, `completed_at_utc`, `completed_at_shanghai`, `outcome`, `reached_stage`, `sealed_ledger_before_sha256`, `sealed_ledger_after_sha256`, `destination`, `published_bundle_sha256`, `published_tree_sha256`, `temporary_authority_absent`, `pipeline_starts`, `automatic_retry_count`, and `error`. Outcome is either `BUNDLE_RECOVERY_PUBLISHED` with a non-null destination/bundle/tree and null error, or `FAILED_NO_AUTOMATIC_RETRY` with an exact error object and no false publication claim.

The exact transition rules are:

1. Failure before claim-root `mkdir`: start not consumed, no claim record; still no automatic retry by the operator.
2. Claim-root `mkdir` succeeds: the start is consumed immediately. A crash before `started.json` is durable may leave an empty or partial claim root; that is still an incomplete consumed recovery and cannot be rerun. After `started.json` is durable but before publication, a caught failure writes `FAILED_NO_AUTOMATIC_RETRY` after safe cleanup.
3. Destination published but terminal not durable: destination plus incomplete claim requires owner reconciliation; it cannot be treated as failure, success, or permission to rerun automatically.
4. Success terminal is written only after destination verification, sealed-ledger after-fingerprint equality, temporary cleanup, and explicit proof that the temporary authority is absent.

Same-authority concurrency is serialized by the atomic claim-root `mkdir`. Distinct authorities racing for the same destination are serialized by atomic no-replace publication; at most one can publish and every losing consumed claim remains non-success.

This claim also closes the crash window that destination absence alone cannot close: a crash before publication must not permit the same authority to start again unnoticed. A destination already present, a pre-existing claim, an aliased/hard-linked path, or an existing temporary authority is a pre-write refusal.

## 6. Recovery algorithm

### 6.1 CLI and pre-write checks

The producer gains a mutually exclusive recovery operation, conceptually:

```text
--recover-sealed-bundle
--bundle-recovery-authorization <path>
```

It cannot be combined with `--execute`, `--preflight-only`, `--attempt-authorization`, or `--expected-ordinal`. The registered thin shim remains byte-identical because it already delegates to `cli_main`.

Before creating the recovery claim or temporary authority, the runtime must:

1. validate the exact process, environment, interpreter, Git hardening, execution head, recovery authority, and epoch-5 lineage;
2. require destination, recovery claim, and temporary authority to be absent;
3. run `validate_live_history` and require `series_closed=true`, exactly one selected candidate, selected ordinal 2, no incomplete record, and no attempt after selection;
4. match the live ledger and every selected started/candidate/terminal/evidence byte to the hashes bound by the recovery authority;
5. require the selected terminal to be `CANDIDATE_VALIDATED_AND_SELECTED` with `automatic_retry_count=0` and no terminal error;
6. open the existing `.series.lock` read-only, acquire a nonblocking shared lock, and hold it from the first ledger snapshot through publication; inability to acquire it is a pre-write refusal;
7. while holding that lock, repeat `validate_live_history`, recheck every recovery-authority-bound ledger/file/root value, and treat only this second result as authoritative; the earlier reads are pre-screening, not the protected snapshot;
8. snapshot the complete ledger tree under the lock and require it to remain byte/mode/link identical through publication;
9. validate both byte anchors in section 7.

An open series, no selected candidate, multiple selected candidates, a missing selected file, changed evidence, changed history root, destination already present, or current epoch drift is rejected before any state write.

### 6.2 Rehydrate, do not replay

Recovery reconstructs two internal sealed-run values from the selected attempt’s existing evidence paths:

- `runs/run-a/root/<registered-artifact-relative-path>`
- `runs/run-b/root/<registered-artifact-relative-path>`

For each run it reads exactly the 14 registered artifacts, verifies regular-file identity and the terminal artifact inventory, recalculates the run Merkle root, and requires:

- run A and run B each have exactly 14 artifacts;
- their maps are byte-identical;
- both roots equal the candidate’s recorded roots;
- the complete evidence-tree root equals the selected terminal/candidate binding.

The sealed `probes/run-a.json` and `probes/run-b.json` are canonical-parsed and checked against their registered exact shapes and safety counters. They are not accepted as opaque bytes merely because the evidence-tree root matches.

A distinct internal type such as `_SealedPipelineReplay` should carry only `run_label`, immutable artifact bytes, and sealed probe evidence. It must not carry an active workspace or execution capability. This prevents an accidental call to active replay from masquerading as archive reconstruction.

Recovery must not call or reference any of the following operational path:

- `SeriesLedger.open` or `allocate_attempt`;
- `replay_selected_pipeline` or `_execute_pipeline_inner`;
- `write_candidate` or `write_terminal` on the series ledger;
- model, network, database, or held-out readers.

The existing bundle schema and archive layout are reused. The builder consumes the sealed run values, the read-only history archive, and the historical selected control anchor. No selected artifact is regenerated.

### 6.3 Passive independent validation

The existing public validator performs active run-A/run-B replay after `_validate_bundle_once`; calling it would violate the zero-pipeline-start requirement. Epoch 5 therefore adds a separate, recovery-capability-gated passive entry point that:

1. resolves and verifies the exact recovery authority and epoch-5 execution binding before reading bundle or ledger bytes;
2. runs the full structural, schema, Merkle, archive, semantic, lineage, void-epoch, filesystem, safety, and selected-history validation;
3. validates both byte anchors described below;
4. never calls `_active_replay_validated_bundle` or `_active_replay_selected_pipeline`.

The passive entry is not a general “skip replay” option. It is callable only with the private recovery delegation derived from the exact owner authority and one-start claim. The ordinary attempt validator retains active replay.

### 6.4 Staging and atomic publication

After bundle construction and passive independent validation:

1. re-read the recovery authority and execution head;
2. revalidate the epoch-5 current control root and loaded-module identity;
3. re-fingerprint the sealed ledger and require exact equality with the preflight snapshot;
4. require destination still absent;
5. publish the already validated staged directory with the existing atomic no-replace primitive;
6. verify the published tree and bundle bytes;
7. re-fingerprint the ledger under the still-held shared lock and prove before/after equality;
8. remove the temporary authority and prove it is absent;
9. only then write the recovery claim’s success terminal.

Any failure is fail-closed, leaves the sealed ledger untouched, emits no attempt terminal, and does not permit automatic retry. A publication race loses safely because no-replace fails. A crash or terminal-write failure after publication leaves a published destination plus incomplete claim and routes to owner reconciliation; it must never be mislabeled success or retried.

## 7. Purpose-form selected-epoch byte correction

### 7.1 The current false identity

Several current checks collapse two distinct claims into one: because epoch 4 produced the selected candidate, they require the process running later bundle work to have current files equal to epoch-4 bytes. After an authorized epoch-5 repair this is impossible by design.

The correction must cover every hidden form of that assumption, not only the epoch table:

- producer `_implementation_epochs` selected-row `require_current`;
- producer `_harness_identity` selected-commit blob validation;
- any post-selection use of `replay_selected_pipeline`;
- validator `_validated_implementation_blob`;
- validator `_validate_harness_identity`;
- validator `_validate_module_identity`;
- validator `_validate_control_archive`, including its per-file current-worktree equality, `_validated_implementation_blob(selected_commit, ...)`, and final `build_control_surface(selected_commit, require_current=True)` calls;
- validator `_validate_implementation_epochs` selected-row worktree comparison;
- any active replay/release path that currently defaults execution identity to selected identity.

The true invariant is a conjunction of two independent anchors.

The code boundary must express that conjunction with two noninterchangeable frozen types, not booleans or optional defaults:

- `HistoricalSelectedAnchor`: selected epoch/commit, action authority/review, selected Git-blob map, archived control root, evidence/history roots; it exposes Git/archive verification only and can never request current bytes.
- `LiveExecutionAnchor`: latest landed epoch/commit, owner authority/review/merge/report, current control surface, loaded producer/validator identities, and exact recovery capability; it exposes current-process verification only and cannot supply selected archive bytes.

`_validate_bundle_once` receives both anchors and an exact validation mode. It passes `HistoricalSelectedAnchor` to `_validate_lineage`, `_validate_harness_identity`, `_validate_archives`, `_validate_control_archive`, `_validate_implementation_epochs`, and historical portions of `_validate_module_identity`. It passes `LiveExecutionAnchor` only to a separate current-execution validator and, for ordinary non-recovery flow, an explicitly authorized active replay. `_validate_archives` and `_validate_control_archive` must reconstruct selected control bytes from epoch-4 Git blobs and bundle archives with `require_current=False`; they must never read epoch-5 current files as expected selected payloads. Producer `_harness_identity` likewise receives the historical anchor and makes its selected blob check explicitly non-current.

No function may accept a single unlabelled `implementation_commit` and infer whether it means selected history or current execution. No missing live anchor may default to the historical anchor. Static signature/call-graph tests enforce those rules.

### 7.2 Historical selected anchor

The selected attempt remains immutably bound to epoch 4:

- epoch and commit come only from the sealed started/action/candidate/terminal/history chain;
- every registered implementation and control-closure byte is read from the immutable Git tree at `890e9002` and checked by SHA-256;
- epoch-4 authority, review, direct-parent topology, exact surface, and execution-head ancestry are still fully validated with `require_current_bytes=False`;
- the recomputed historical control root must equal the action authorization, candidate, terminal/archive, and bundle control archive;
- bundle `harness_identity`, selected lineage, and control archive continue to describe epoch 4, never epoch 5.

No worktree byte is allowed to substitute for the selected Git blob. Git-blob mismatch, selected commit substitution, action-root drift, archived-control drift, or ledger/evidence mutation remains fatal.

### 7.3 Live execution anchor

Every post-selection operation that executes code is independently bound to the latest fully landed and reviewed epoch, which for this recovery will be epoch 5:

- recovery authority names the exact epoch-5 implementation, owner surface authority, independent review, landing merge/report, and control root;
- implementation is the direct child of the owner authority; review is its direct unique-`A` child; landing preserves both objects with the review as the merge’s exact second parent;
- the epoch-5 implementation is the latest complete landed epoch chain visible on the execution head; ambiguity or a later landed epoch rejects the authority;
- all current 73 repository control members and runtime inventory must equal the epoch-5 reviewed Git blobs via `build_control_surface(epoch5, require_current=True)`;
- loaded producer and validator module origins and digests must equal epoch-5 blobs;
- execution head, current bytes, and imported-module identity are rechecked immediately before publication.

“Latest complete landed epoch” is a machine predicate, not a statement copied from the recovery authority:

1. The authority supplies exact refs for epoch-5 surface authority, implementation, review, merge, and landing report.
2. The runtime requires: authority is a unique first-parent `A`; implementation is its direct single-parent child with the exact authorized surface; review is the implementation’s direct single-parent unique-`A` child; merge has exact second parent equal to the review; landing-report commit is the merge’s direct single-parent child and uniquely adds only that report.
3. The landing-report commit must lie on the execution head’s first-parent ancestry. Side-branch objects not reachable on that ancestry are not “landed.”
4. The runtime enumerates every first-parent-added JSON report reachable through the execution head and strictly parses every document matching the registered epoch surface-authority, implementation-review, or landing-report schema/path family. Malformed matching candidates are errors, not ignored files.
5. Among reachable six-field surface authorities, epoch numbers are unique. The maximum epoch must be 5 and its exact authority must equal the recovery record. A duplicate epoch 5 or any reachable authority for epoch greater than 5 is rejected even if its implementation/review/landing chain is incomplete.
6. The exact epoch-5 complete chain must be unique. Any later reachable implementation review or landing artifact that claims epoch 5 or higher, including an incomplete higher chain, is an ambiguity and rejects recovery.
7. From the epoch-5 merge through the execution head, no first-parent diff may touch any of the 73 repository control members. Current full-control equality to epoch-5 Git blobs is then checked independently, catching uncommitted drift as well.

Thus a stale authority cannot self-declare itself latest, a higher partial governance chain cannot be silently ignored, and a later complete landing requires a newly reviewed recovery design/authority rather than fallback.

There is no fallback from a missing/invalid live execution binding to the historical selected commit. Passive validation may prove historical bytes without executing the pipeline, but any executing entry point must have a valid live anchor.

### 7.3.1 Recovered-bundle release consumption

Recovery must not publish a bundle that the formal release consumer can validate only by rerunning the pipeline. A recovered bundle therefore has a separate capability-gated release validation route:

- it consumes the unchanged release receipt/schema plus the committed recovery authority and successful recovery claim;
- it invokes `_validate_bundle_once` with `HistoricalSelectedAnchor(epoch4)`, `LiveExecutionAnchor(epoch5)`, and passive recovered-release mode;
- it performs all release/bundle cross-equalities, immutable Git and archive checks, exact published-bundle byte checks, recovery-claim/destination binding, and the current epoch-5 anchor recheck;
- it never calls `_active_replay_validated_bundle` or `_active_replay_selected_pipeline`.

The ordinary release validator retains active replay for an ordinary attempt-built bundle and must reject a recovery-produced destination when the exact recovery capability/claim is absent. The release receipt and bundle schemas remain byte-for-byte unchanged; the distinction is an internal validated capability derived from committed recovery evidence. This prevents the recovery from succeeding only to hit the same selected-current or zero-pipeline conflict at the next registered consumer.

### 7.4 Why tamper control is preserved

The old rule tried to prove two different times with one equality:

`current process bytes == selected attempt bytes`.

That equality was sufficient only while no approved repair had landed. It becomes both false and unsafe after epoch 5 because it would force recovery to execute obsolete code.

The proposed rule is stronger and temporally correct:

```text
sealed candidate bytes == immutable selected Git blobs at epoch 4
AND
executing process bytes == latest landed, owner-authorized, independently reviewed Git blobs at epoch 5
```

Every byte remains covered:

- historical tampering changes a Git/blob digest, control Merkle root, action/candidate/terminal root, evidence root, or history root;
- live tampering changes a current-file digest, full control root, loaded-module digest/origin, or prepublication recheck;
- lineage substitution breaks authority/review/parent/merge/ancestor predicates;
- crossing the anchors is impossible because the bundle records selected epoch 4 while the private recovery capability records execution epoch 5.

The correction removes only the invalid assumption that historical provenance and present execution must be the same commit. It does not relax membership, current-byte coverage, immutable-blob coverage, or any gate.
