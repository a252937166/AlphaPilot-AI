# P4.2a 独立复核交接契约

Status: `AUTHORITATIVE_SUCCESSION_CONTRACT`

本文件由独立复核方 `independent_ai_architect_claude_code` 在其参与终止前写就，交给操作方 Codex 与业主 ouyang。它不是设计提案，不是裁定书，不授予任何执行权限。它记录三件事：哪些事实不可移动、哪些判断在复核方缺席后不能再由操作方自己做、剩下的路怎么走完。

写这份东西的理由很直接：过去三周里，实现方与复核方的每一次分歧都揭出了一个真实缺陷。C-9、C-13、C-15、F-17、F-18、D-1 无一例外是"一方写、另一方以怀疑姿态重算"发现的。这个结构即将只剩一方。文档替代不了第二双眼睛，只能把能固化的部分固化，把不能固化的部分明确交还给业主。

## 1. 生效条件与地位

自复核方停止参与之日起生效，直至业主指定新的独立复核方并在 main 上留下 create-only 记录为止。

本文件与既有治理文件的关系：**它不覆盖任何已落地的裁定、授权或契约**。冲突时以已落地的 create-only 文书为准，本文件仅补充"复核方不在场时怎么办"。

## 2. 治理变更的诚实记录

独立 AI 复核在 2026-08-29 之后中断。这意味着从此刻起：

- 任何产物**不得**声称经过独立复核，除非确有第二方执行；
- F-12（复核方独立跑完两个完整注册模块）**没有**自动的替代品，替代方案见第 10 节；
- 六字段 surface authority 中 `owner.identity = "ouyang"` 的语义不变：业主本人当面确认，复核方转达的通道消失后，业主直接向操作方确认，并要求操作方在 B 文档的 `source` 字段如实写明"业主直接向操作方确认"，**不得**继续沿用"业主向复核方当面确认，由复核方转达"这句话；
- 已落地的历史文书中该字段保持原样，那些确实是转达的。

**把操作方自测标注成独立复核，是这套体系里最严重的一种造假。** 宁可标注"操作方自测，无独立复核"，产物照样有效，只是证据等级降一级。

## 4. 硬规矩

1. **create-only**：治理文书一经提交永不修改、永不删除。写错了就再写一份更正，把错的那份留在历史里。
2. **merge-only 落地**：实现分支永远用 merge 落地，保留实现对象与评审对象两个父。禁止 rebase、squash、amend、cherry-pick、force push。
3. **唯一 A**：每份治理文书只能有一次 status-A 触碰。例外只有一种——合并的 first-parent 投影，且投影处的 blob 字节与钉住摘要逐字节相同（epoch-7 的九条判据）。**不得**为了让谓词通过而删除任何引用或分支；2026-08-27 删除 `origin/codex/fix-backend-ci-portability` 之前先做了 git bundle 双副本归档（SHA `79892841a00c45cdd84fddeb762c64bbb9bbc5e519a701e114237b6507d7cd1f`），照这个规格办。
4. **失败永不消失**：失败的轮次、被否的候选、偏离流程的记录，全部保留并如实记述。不得删除、不得改写、不得事后美化。
5. **账本与镜像只读**：见 3.3。丢失的字节**不得**从摘要反向重建——摘要能验证字节，不能生成字节。
6. **仓库是公开的**：`.env`、密钥、令牌永不提交。数据库备份永不进 GitHub（单文件 5GB 超限，而且会把全部新闻与交易数据公开）。
7. **交易只允许 SIMULATE**：六个锁全部 false，任何解锁需要业主的独立授权文书。
8. **退役的 heldout id 永不复用。**
9. **heldout 评估是一次性的**：`heldout_evaluation_one_shot` 消费掉就没有第二次。在它之前的一切都必须先绿。
10. **静态门 PASS 会被字节变更作废**：producer 或 validator 任一字节改动，此前所有静态门、mypy、测试结论一律作废重跑。曾经有一次 strict-mypy 的绿色被跨改动继承，是复核方重算才发现的。

### 可以自证（验收标准是机器判定的）

- 两个注册测试模块的通过与否、节点数、耗时
- ruff / mypy strict
- 持久全量门禁结果

- 真实血统普查（`p4.2a-v2-2-real-lineage-census-v1`）
- §12.6 工作上界 counters（补齐后）
- pre-start 探针的耗时、最大 RSS、swapouts 增量

### 不可自证（必须业主亲自做或如实降级标注）

- **F-12**：独立复核方跑完两个完整模块。替代程序见第 10 节。
- **设计评审**：任何新增能力、新增谓词、新的 epoch 方向，不能由写它的人判它通过。业主可以自己读设计并批准，也可以接受"未经独立设计评审"的标注。

- **Q→R→B 里的业主确认**：必须业主本人给出确认原话，操作方逐字绑定，`source` 如实写明确认渠道。
- **release 决定**：业主的判断，不是机器判定。
- **裁定"失败归因"**：这次三连误判（主机不安静 → 内存缺陷 → census）说明归因判断最容易出错。归因写进文书前必须有单进程测量或调用图证明，只有系统级指标不够（C-15）。

## 7. 剩余序列与验收标准

### 7.1 当前阻断点

F-15 BLOCKED。两项修复必须完成（裁定 `df800d6`）：

**修复一 · pre-start 性能。** 根因是 `SeriesLedger.allocate_attempt` 的 continuation mirror 校验与 second-copy history 校验：`_strict_private_tree_inventory` 保留每个文件的全量 payload，`_validate_second_copy_history` 同时持有 primary、replay-bound primary 与多份快照 inventory。实测 175.18 秒 / 180 秒预算，余量 4.82 秒。

- 180 秒**不得**上调、放宽、可配置化或绕过
- 不得削弱任何校验，今天证明的事实必须继续以同等强度证明
- 走 epoch-6 r2（`e5aab977`）的 commitment fingerprint 先例：名字绑到封档时的 root，热路径停止读 payload
- **输出同一性要证明**：同一 premirror 状态必须复现 `started.json` = `ffd15b310c1b72ac3a317240db1b7a2dd64005015bc2ef251e86b785cb4f2d1a`
- 验收线：standalone premirror 探针 ≤ 60 秒（三倍余量），报耗时、最大 RSS、swapouts 增量

**修复二 · §12.6 counters。** counters 记录 census 实际执行的 Git 对象与子进程工作量而非事后估算；上界增量式评估，census 进行中即可 fail fast；validator 独立重算不采信 producer 报数；两模块各有真实 census 对上界的注册测试，含压线正例与中途触发的负例。

## 8. 历史陷阱

### 8.1 主机事实

- 系统时区 EDT，业务时间 CST，差 12 小时，数据库里是 UTC。三套时间不要混。
- 调度器是 gui LaunchAgent，跑的是**工作区字节**（editable 安装）。未提交的改动一重启就上线。断言代码血统必须比对 blob SHA，不能只看提交。
- 磁盘接近满会卡住 swap 扩容，表现为 kernel_task 高占用、整机发木、长测超时。先看 `df -h /System/Volumes/Data` 和 `sysctl vm.swapusage`，别急着杀进程。
- 「系统设置」停在存储页面会反复拉起全盘体积扫描（`ApplicationsStorageExtension`），单进程吃满一核。长测前关掉。
- zsh 不对未加引号的变量做词分割，`for x in $LIST` 会把整个字符串当一个词。写清理脚本时逐行读文件。

### 8.2 编号发现（详见各自的裁定书）

C 系列是复核方自己的错误：C-9 授权变更 epoch 时未核对 packer 可接受的序列形态；C-12 门禁健康谓词写得过宽，拦下三次本该放行的运行；C-13 批了 11 键指纹集又知道谓词形态却没把两者连起来；C-15 用系统级 swap 增长推断分配者身份。**共同点是：批准某物与理解其后果之间存在缝隙。**

F 系列是流程要求：F-12 复核方跑完整模块；F-14 最新落地 epoch 谓词；F-15 操作方交付前跑完整模块，且六小时的 F-12 不能是首次执行；F-17 每尝试成本超线性（recursive fingerprint 累积）；F-18 读真实仓库的 bundle 阶段谓词必须也在真实仓库上做只读预演，合成夹具见证不了 ref 污染。

### 8.3 反复出现的失效模式

**"下一堵墙"**：一个版本做完，在下一个阶段才撞死。epoch 3、4 被它吃掉，D-1 是同一类（epoch-7 落地后 release 复验必挂）。**防法：任何改动都要沿整条消费链往后推演一遍，问"这个改完之后，下游哪个还会拿旧假设来验它"。**

**合成夹具与真实仓库的分歧**：bundle 阶段谓词只在合成 git 仓上测过，撞上真实历史里的合并投影就崩（F-18）。

**归因过早**：见 C-15。

## 9. 卡住时的升级规则

操作方遇到以下任一情况，**停下来交给业主**，不要自行裁定：

1. 需要移动任何冻结契约成员；
2. 需要放宽任何注册常量（超时、上界、阈值、样本数）；
3. 需要新增能力或新谓词而无对应的已批准设计；
4. 失败归因指向"环境问题"而没有单进程测量支撑；
5. 任何涉及删除、重写、覆盖既有证据的动作；
6. 连续两轮同一处失败。

升级时提交一份 create-only 的现状文书：观测到什么、复算了什么、有哪些互斥假设、每个假设需要什么证据来证伪。**不要**在文书里给出自己偏好的结论然后请业主追认。
